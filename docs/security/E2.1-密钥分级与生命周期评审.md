## 0. 结论摘要

对《密钥管理与签名方案.md》v1.0 的整体评审结论为 **有条件通过**：

- **主体架构评审通过**：五类密钥分离（平台/资产/策略/发布/OTA）方向正确，符合「单点泄露不波及其他域」的最小化原则；轮换与吊销流程骨架完整；CRL 与证书固定机制有定义。
- **存在 4 项必须整改项（阻断发布）**：
  1. **开发/生产密钥混淆风险**：方案 §3.2 将开发密钥以明文 `*.pk8` 形式入库（虽 gitignore 但允许存在于工作区），且 `keys/` 目录当前已存在开发用 `platform.key`/`policy.key` 等真实私钥文件——**生产密钥与开发密钥必须物理隔离**，当前仓库结构存在把开发密钥误用于生产签名的风险。
  2. **算法与长度的 NIST 对齐缺口**：方案沿用 RSA 2048/3072，但 2026 年 NIST SP 800-57 Rev.5 对「平台/OTA 这类长期根密钥」建议 **RSA 3072 或 ECC P-384**，RSA 2048 仅限短生命周期（≤2030）且不应作为根/发布密钥长期锚点；发布密钥（10 年）用 RSA 2048 需要论证或升配。
  3. **吊销口径不闭环**：CRL 只有「系统启动/策略包加载/资产包安装/每周更新」四类触发，缺少**紧急推送路径与时间 SLA**（对齐 R9.9 票据吊销 ≤1 分钟的红线）；且平台密钥吊销「需 OTA 推送新证书」未定义新证书的信任根更替机制（certificate rotation bootstrap），存在「吊销即砖」或「吊销不可达」风险。
  4. **密钥使用审计粒度不足**：§9.2 只要求「记录签名操作」+ 保留 7 年，未定义**每个签名操作的可校验证据**（被签内容的哈希、签名值、请求方身份、策略版本），无法与 E5.1「审计链篡改」红队方法对齐——密钥使用事件应进入 `IAgentAuditService` 的 `CAT_SYSTEM` 审计链并附带 `payloadHash`。

- **3 项建议整改项（建议发布前完成）**：
  1. 明确「发布密钥」与「大脑 App 签名」的关系：当前 `release.keystore` 用 keytool 生成、口令明文写入脚本——**口令必须进密码管理器/CI secret**，脚本只留占位符。
  2. 增加「密钥分级矩阵与吊销时效」的验收测试脚本（建议接入 E1.2 CI 安全门：`keys/` 目录不得包含生产私钥、私钥权限必须 600、密钥清单与证书指纹文件对账）。
  3. 为 OTA 密钥补充「密钥更替（rollover）协议」：新根信任如何注入存量设备（推荐在固件内置「轮换锚点」或双根并存窗口）。

## 2. 评审正文

### 2.1 密钥分离设计（平台/资产/策略/发布/OTA）

**评审结论：通过（方向正确，落地需整改 #1）**

方案定义的 5 类密钥分离符合 E1.1「单点泄露不波及其他域」的最小化原则，且与系统资产形态一一对应：

| 密钥 | 签名对象 | 对应 D 草案资产 | 风险等级 |
|---|---|---|---|
| 平台密钥 | SystemUI/Settings/framework | D5/D12 界面 + 平台签名 | **高**（泄露=整个系统可信边界崩塌） |
| 资产密钥 | Skill/DMI/Macro 资产包 | D11 资产目录 | 中（资产生态） |
| 策略密钥 | DSL 规则包（PolicyPack） | D17 策略 DSL + D10 热更新 | **高**（策略=安全裁决本体，泄露=攻击者自签策略） |
| 发布密钥 | 大脑 APK | D3 Agent 运行时 | 中高（大脑=特权应用） |
| OTA 密钥 | 系统更新包 | 架构 §7 OTA | **高**（泄露=全量设备可被签名恶意固件） |

**关键评审点**：
- ✅ 策略密钥独立于平台密钥是正确的——策略包走 `reloadPolicySet` 热更新（D10），其密钥不应与 APK 签名共享，否则 OTA 外的策略通道等于打开了第二个平台签名面。
- ✅ 资产密钥独立，支持第三方 Skill 生态（D14）时可按「每资产商/每安全等级」进一步拆分，当前一把资产密钥是**生态层面的集中点**（整改建议 C 项）。
- ⚠️ **缺口（整改 #1）**：方案 §3.2「开发环境密钥管理」允许 `keys/` 下明文存放 `platform.pk8` 等，且权限 `chmod 600` 只是 POSIX 语义，**Windows 开发机/构建机没有该语义**——项目当前在 Windows 上构建，`keys/` 内已有明文私钥，须在 CI 与构建脚本中强制隔离（见 §2.3）。

### 2.2 密钥强度与算法（NIST SP 800-57 对标）

**评审结论：有条件通过（整改 #2）**

| 方案条目 | 评审意见 |
|---|---|
| RSA 4096 平台/OTA | ✅ 达标（≥3072，安全生命周期 >2030） |
| RSA 2048 资产 | ⚠️ 边缘可接受（资产生命周期 10 年，2048 在 2030 后进入风险区，建议升 3072） |
| RSA 3072 策略 | ✅ 达标 |
| **RSA 2048 发布** | ❌ **不达标**：发布密钥有效期 10 年（2026-2036），NIST SP 800-57 Rev.5 明确 2048 位 RSA 的合理使用期不晚于 2030；大脑 APK 是最高权限应用，其签名密钥应 **3072 或 ECC P-384** |
| 有效期配置 | ⚠️ 平台/OTA 25 年与「设备生命周期 10-15 年」表述不一致，建议统一为「≥ 设备最大生命周期」并设明确失效策略 |

**整改 #2 具体建议**：
- 发布密钥升配 RSA 3072（或 ECC P-384，Android APK 签名 v2/v3 均支持），并把 `-keysize 2048` 改为 `3072`；
- 在文档 §1.2 增加「密钥强度退役表」：任何密钥在 NIST 推荐退役年前 2 年必须完成轮换或升配。

### 2.3 密钥存储与访问控制

**评审结论：有条件通过（整改 #1 为主）**

- ✅ HSM/TPM 分级、双人授权、角色分离、操作审计的原则定义正确。
- ✅ `.gitignore` 排除 `*.pk8`/`*.keystore` 正确。
- ❌ **关键缺口**：方案 §3.2 明示「开发环境用加密文件」，但仓库 `keys/` 中实际存在明文开发私钥（`platform.key` 等），且 `generate_dev_keys.ps1` 生成后就地落盘。**这些私钥一旦被误认为生产密钥签名发布包，等于把开发用弱口令/明文密钥带入生产**。
  - **整改要求**：① 目录重命名 `keys/` → `keys/dev/` 并明确标注 DEV-ONLY；② 生产密钥禁止进入代码仓库（含构建镜像），改由「构建时从 HSM/KMS 注入」；③ 新增 `ci/security-gate` 检查：`keys/` 顶层不得出现 `*.key`/`*.pk8`/`*.keystore`（已在 E1.2 落地建议中）。
- ⚠️ `release.keystore` 的 `<STRONG_PASSWORD>` 占位符若被真实口令替换并入库，即属 R4.5「secret 值不得写入日志/文件」红线违反——**口令必须走 CI secret**。

### 2.4 签名流程

**评审结论：通过（覆盖完整，工具链需补验证）**

方案覆盖 5 类签名流程（signapk/jarsigner/openssl dgst/sign_target_files_apks），与系统构建链匹配。评审补充两点：
- APK 使用 **APK Signature Scheme v3（rotating key 支持）**，为发布密钥轮换预留结构（当前文档用 jarsigner v1，建议升级描述）。
- 资产/策略包的签名采用「SHA-256 + 私钥签名」分离方式（`asset.zip.sha256` + `asset.zip.sig`），需明确**验签侧必须校验「哈希文件与签名一致」且拒绝哈希文件本身被替换**（防「哈希交换攻击」——攻击者同时替换 hash 与 sig）。建议改为单一签名负载（对包内容直接签名）或把哈希文件也纳入签名覆盖。

### 2.5 证书信任链与证书固定

**评审结论：通过（机制存在，缺紧急更新路径）**

- ✅ 平台/资产/策略证书 SHA-256 指纹在 `CertificatePinning.java` 固定，与「域名白名单 + 证书固定」的架构 §6 一致。
- ⚠️ `certificate_fingerprints.txt` 已存在（实际指纹），需保证该文件与 `keys/*.crt` **对账**（建议接入 E1.2 CI 检查）。
- ❌ **缺口（整改 #3）**：CRL 更新只有周更 + 事件触发，缺少「紧急吊销」通道。对齐红线 R9.9（票据吊销 ≤1 分钟），密钥级 CRL 至少需要：**云端 CRL 短时缓存 + 设备端 TTL ≤1 分钟 + 紧急推送（FCM/OTA 轻量）**。平台密钥泄露时「7-14 天恢复」的估计在攻击者已能签任意系统应用的场景下不可接受——需「检测即停用受影响签名服务 + 快速吊销锚点」。

### 2.6 密钥轮换与吊销

**评审结论：有条件通过（整改 #3 为关键）**

- ✅ 资产/策略/发布密钥的定期轮换周期（3/5/2 年）与 90 天双证书共存期设计合理。
- ✅ 平台/OTA「设备生命周期内不轮换、泄露紧急轮换」符合 Android 平台惯例。
- ❌ 平台密钥轮换缺少**新根信任注入协议**：Android 设备升级平台密钥需要系统级信任根更替，当前方案仅「OTA 推送新证书」一句带过。建议：
  1. 设备出厂固件内置「轮换锚点」机制（镜像内同时信任当前与下一代平台根）；
  2. 平台密钥泄露时先**吊销并 stop-the-line 停止新签名发布**，再用锚点机制注入新根 + 批量 OTA；
  3. 该流程须进 E5.1 红队「密钥侧」用例。

### 2.7 应急响应与备份恢复

**评审结论：通过（原则正确）**

- ✅ 泄露影响分级（平台/OTA 严重、资产/策略中、发布低）合理。
- ✅ Shamir 3/5 秘密拆分 + AES-256-GCM 备份 + 季度恢复演练的原则正确。
- ⚠️ 补充：备份的**可用性验证**（不是只验证备份存在）应纳入每季度演练——「恢复演练」应包含「用备份实际完成一次生产级签名」。

### 2.8 密钥使用审计（对齐审计链红线）

**评审结论：需整改（整改 #4）**

方案 §9.2 要求记录签名事件并保留 7 年，但审计粒度不足。对齐 E1.1 R8.1-R8.5 与 `IAgentAuditService`：
- **必须**：每次密钥使用（签名操作）写入审计事件 `CAT_SYSTEM`，字段含 `key_type`、`operator`（构建机/请求方身份）、`target`（被签内容引用）、**`payloadHash`（被签内容哈希，不存明文）**、`result`、`signature`（可选）。
- **必须**：审计事件进入不可变哈希链（防「密钥被滥用后删审计」），与 E5.1「审计链篡改」用例对齐。
- **建议**：构建机上的密钥使用日志与密钥管理后台（HSM audit log）**对账**，覆盖「HSM 记了但构建日志没记」的盲区。

## 5. 遗留项（非阻断，随里程碑滚动）

1. **多大脑信任根**（对齐 D3 §6 开放问题 5）：将来第二个特权大脑的 agentId 签发与证书防伪——需要专门设计，列入 A5 预研。
2. **HSM 选型与采购**：FIPS 140-2 L3 的物理 HSM/云 KMS 尚未落地，当前为方案层；A1 阶段可用「构建机隔离 + 加密文件 + CI secret」过渡，A2 前须定 HSM/KMS。
3. **Windows 构建机的密钥保护**：POSIX `chmod 600` 在 Windows 无效，需用 EFS/bitlocker/凭据保险库方案替代，随构建环境搭建补充。
4. **OTA 密钥签名完整性**：与架构 §7「可信启动同款校验」衔接的密钥链验证（bootloader → boot → system → OTA）需在 A 系列后续验证。
