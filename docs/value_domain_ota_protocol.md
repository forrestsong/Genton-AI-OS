# C6.4 值域知识库 OTA 更新协议规范

## 1. 概述

本文档定义值域知识库的 OTA（Over-The-Air）更新协议，用于在设备上安全地更新策略 DSL 的值域定义和分类器模型版本绑定。

## 2. 更新触发场景

### 2.1 模型 OTA 更新触发
当 NotificationClassifier 或 SpamScorer 模型通过 OTA 更新时：
1. 模型管理器（ResidentModelManager）检测到新模型版本
2. 查询 ValueDomainVersionManager 检查值域兼容性
3. 如果不兼容，阻止模型加载并告警
4. 如果兼容，允许模型加载

### 2.2 值域知识库主动更新
当 PolicyPack 版本更新时：
1. 系统接收到值域知识库 OTA 包
2. ValueDomainVersionManager 验证版本和签名
3. 更新值域知识库
4. 通知 PolicyEngine 重新加载策略规则

### 2.3 策略规则更新触发
当策略规则引用新的 category 值时：
1. DSL 编译器检测到未知的 category 值
2. 查询 ValueDomainVersionManager 获取最新值域
3. 如果本地值域过时，触发 OTA 更新

## 3. OTA 包格式

### 3.1 包结构
```
value_domain_ota_v1.0.1.zip
├── value_domain_catalog_v1.yaml  # 值域知识库文件
└── ota_metadata.json              # OTA 元数据
```

### 3.2 ota_metadata.json 格式
```json
{
  "package_version": "1.0.1",
  "package_type": "value_domain_update",
  "created_at": "2026-09-07T10:30:00Z",
  "files": [
    {
      "name": "value_domain_catalog_v1.yaml",
      "checksum": "sha256_hash_here"
    }
  ],
  "release_notes": "Added new notification categories for email classification"
}
```

## 4. 版本校验规则

### 4.1 版本号递增检查
- 新版本号必须大于当前版本号
- 使用语义化版本规范（major.minor.patch）
- 降级更新被拒绝（除非显式回滚）

### 4.2 分类器版本绑定检查
- `notification_classifier` 版本必须与已部署的模型版本匹配
- `spam_scorer` 版本必须与已部署的模型版本匹配
- 版本不匹配时，OTA 更新失败

### 4.3 策略引擎兼容性检查
- 检查 `min_policy_engine_version`
- 如果设备策略引擎版本过低，拒绝更新
- 提示用户升级系统固件

### 4.4 更新通道检查
- 更新通道必须一致（stable/beta/dev）
- 跨通道更新被拒绝
- 用户可手动切换更新通道

## 5. 安全验证流程

### 5.1 签名验证
```
1. 提取 OTA 包中的签名
2. 使用平台公钥验证签名
3. 签名验证失败 → 拒绝更新
4. 签名验证通过 → 继续
```

### 5.2 校验和验证
```
1. 计算值域知识库文件的 SHA256
2. 与 metadata.checksum_sha256 比对
3. 不匹配 → 拒绝更新（文件损坏）
4. 匹配 → 继续
```

### 5.3 完整性验证
```
1. 解析 YAML 文件
2. 校验必需字段完整性
3. 校验值域枚举格式
4. 格式错误 → 拒绝更新
5. 格式正确 → 继续
```

## 6. 更新流程

### 6.1 正常更新流程
```
1. 接收 OTA 包
2. 版本校验（递增、兼容性）
3. 安全验证（签名、校验和、完整性）
4. 备份当前版本（用于回滚）
5. 应用新版本
6. 通知 PolicyEngine 重新加载
7. 通知监听器（ResidentModelManager、DSL 编译器）
8. 记录更新日志
```

### 6.2 失败处理流程
```
1. 更新失败（任一步骤）
2. 保留当前版本不变
3. 记录失败原因
4. 上报遥测数据
5. 通知用户（可选）
```

### 6.3 回滚流程
```
1. 检测到严重问题（如策略编译失败）
2. 查找回滚目标版本
3. 验证回滚版本可用性
4. 应用回滚版本
5. 通知 PolicyEngine 重新加载
6. 记录回滚事件
```

## 7. 灰度发布策略

### 7.1 灰度分批
```
第 1 批：内部测试设备（1%）
第 2 批：Beta 用户（5%）
第 3 批：早期采用者（10%）
第 4 批：主流用户（50%）
第 5 批：剩余用户（100%）
```

### 7.2 灰度暂停条件
- 错误率 >5%
- 回滚率 >2%
- 用户投诉激增
- 发现严重 Bug

### 7.3 灰度回滚条件
- 错误率 >10%
- 系统崩溃率上升
- 数据完整性问题

## 8. 监控和遥测

### 8.1 更新成功率

### 8.2 更新延迟
- 下载耗时

- 应用耗时
- 总耗时 P95：<10 秒

### 8.3 回滚统计

- 回滚原因分布
- 回滚率阈值：<1%

## 9. 错误码定义

| 错误码 | 说明 | 处理建议 |
|-------|------|---------|
| 1001 | 版本号无效 | 检查 OTA 包版本号格式 |
| 1002 | 版本递增检查失败 | 新版本号必须大于当前版本 |
| 1003 | 更新通道不匹配 | 切换到正确的更新通道 |
| 2001 | 签名验证失败 | OTA 包可能被篡改，拒绝更新 |
| 2002 | 校验和验证失败 | 文件损坏，重新下载 OTA 包 |
| 2003 | 完整性验证失败 | YAML 格式错误 |
| 3001 | 分类器版本不兼容 | 先更新分类器模型 |
| 3002 | 策略引擎版本过低 | 升级系统固件 |
| 4001 | 备份失败 | 磁盘空间不足 |
| 4002 | 应用更新失败 | 文件系统错误 |
| 5001 | 回滚版本不存在 | 无法回滚 |

## 11. 测试用例

### 11.1 正常更新测试
1. 准备 OTA 包（版本 1.0.0 → 1.0.1）
2. 执行更新
3. 验证版本号已更新
4. 验证 PolicyEngine 已重新加载
5. 验证新 category 值可用

### 11.2 版本回退测试
1. 尝试安装旧版本（1.0.1 → 1.0.0）
2. 验证更新被拒绝
3. 验证当前版本未改变

### 11.3 签名验证测试
1. 准备未签名的 OTA 包
2. 执行更新
3. 验证签名验证失败
4. 验证更新被拒绝

### 11.4 兼容性测试
1. 准备不兼容的 OTA 包（分类器版本不匹配）
2. 执行更新
3. 验证兼容性检查失败
4. 验证更新被拒绝

### 11.5 回滚测试
1. 备份当前版本（1.0.1）
2. 更新到新版本（1.0.2）
3. 触发回滚
4. 验证回滚到 1.0.1
5. 验证 PolicyEngine 已重新加载

## 13. 常见问题

### Q1: 如果值域知识库更新失败，系统还能正常工作吗？
A: 是的。更新失败时保留当前版本不变，系统继续使用旧版本的值域知识库。

### Q2: 值域知识库更新需要重启设备吗？
A: 不需要。ValueDomainVersionManager 支持热更新，PolicyEngine 会自动重新加载。

### Q3: 如何处理分类器模型版本与值域知识库不匹配的情况？
A: ValueDomainVersionManager 会阻止不兼容的模型加载，并告警提示先更新值域知识库。

### Q4: OTA 更新包的大小限制是多少？
A: 值域知识库 YAML 文件通常 <100KB，OTA 包限制为 1MB。

### Q5: 回滚操作会丢失用户自定义的策略规则吗？
A: 不会。用户自定义规则（user.* 命名空间）独立存储，不受值域知识库更新影响。
