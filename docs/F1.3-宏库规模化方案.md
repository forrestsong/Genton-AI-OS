## 1. 目标与验收口径

宏库规模化（宏库 v1）的目标是在**可控质量**下把宏资产从"个位数的验证样例"扩充到
**按机型分层的生产级宏库**，并满足 A5 门禁的硬性验收：

> **A5 门禁（WBS §10.2）：宏通过率 ≥99%**（同机型黄金样例通过率），
> 误预取 <2%，7 天冷静期与抑制窗行为正确（后者属 C2/D4.2 learn 域，本方案只承接宏侧）。

本方案定义四条主线：

1. **per-机型样本扩充**（§3）：黄金样例按机型档案分层，样本数量与覆盖维度随机型分档提升；
2. **staged-enable 观察**（§4）：新宏先 staged，经回归/观察数据达标后才 enable（对齐 A8.1 三方资产初始 staged）；
3. **通过率 ≥99% 验收配合**（§5）：通过率口径、统计窗口、达标判定与 H 部门验收联动；
4. **增量回归策略**（§6）：全量回归之外，按影响面只跑受影响的宏，缩短回归周期。

## 2. 数据基础（F4.1 / F4.2 的衔接）

宏库规模化直接消费两个既有完成品：

- **F4.1 机型校准矩阵**（`reports/F4.1_机型校准矩阵.md`）：机型档案（`vendor/genton/config/calibration/profiles/*.json`）
  提供每机型的分级（P0/P1/P2）、坐标归一化基数、等待阈值、降采样参数、DMI 可用性、S7 能力位；
- **F4.2 校准回归样本库**（`reports/F4.2_校准回归样本库.md`）：per-机型黄金集（`regression/*.suite.json`），
  覆盖 coordinate/replay/timing/downsample/dmi_gate/s7_gate 六类，供 H4.1 真机矩阵执行。

**分工**：F4.2 的 suite 验证的是"**机型校准基线**"（参数/阈值/能力位）；F1.3 的黄金样例验证的是
"**宏资产行为**"（用户操作序列在指定机型上的结果）。两者共用设备矩阵，但对象不同：
F1.3 样例以 `deviceTags` 引用机型档案，宏执行时套用 F4.1 的坐标缩放与等待参数。

## 3. per-机型样本扩充

### 3.1 分层目标（宏库 v1 规模）

| 机型分级 | 目标宏数 | 每宏黄金样例数 | 覆盖维度 |
|---|---|---|---|
| P0（旗舰，sm8550_p0） | ≥ 30 | ≥ 3（同机型） | 混合/纯坐标/纯感知三策略、冷启动、重复执行、断网 |
| P1（中端，mt6897_p1） | ≥ 20 | ≥ 3 | 混合策略为主、降采样、能力裁剪后跳过项 |
| P2（入门） | ≥ 10 | ≥ 2 | 纯坐标/混合、降载参数下限 |

> 首期以 F4.1 已建档的 **sm8550_p0 / mt6897_p1** 为起点（各 2 条黄金样例已在
> `tests/macro/golden/` 就位，作为种子），后续随 A12.2 机型能力位确认扩展档案。
> 样本量建议 **黄金样例 100 条级**进入 A5 验收（含多机型重复，去重后宏数约 40–60）。

### 3.2 样本扩充流程

```
选题（高频用户意图 + 可用 DMI 缺失兜底）
  → F1.1 录制（per 机型）→ 脚本生成（选择策略）
  → 真机人工验证（黄金化）→ 写 tests/macro/golden/<macro>.json
  → F1.2 CI 静态校验 + 设备重放 → staged-enable 观察 → enable
```

**每机型必做适配**（套用 F4.1 档案）：
- 坐标缩放：`macro.coordinateScaleX/Y`（无则 1:1，万分比归一化已兜底分辨率差异）；
- 等待阈值：`timing.waitInsertThresholdMs`（默认 300）/ clamp 100–5000；
- 感知策略选择：按 `macro.supportedStrategies`（0/1/2）——跨机型建议 HYBRID（1）；
- 能力裁剪：P1 无 AON 岛、采样率 <800Hz 等 → 该机型样例 `onUnsupported=skip`（不得记为失败）。

### 3.3 样例字段约定（F1.2 扩展，见 `tests/macro/golden/README.md`）

- `macroVersion`：SemVer，供版本基线管理；
- `deviceTags`：适用机型档案 ID 列表（`sm8550_p0` / `mt6897_p1`），增量回归的筛选键；
- `perceptionStrategy`：0/1/2（对齐 F1.1）。

### 3.4 样本质量红线

1. 黄金样例必须**人工验证通过**后才能入库（`isGolden=true` 且不来自自动化猜测）；
2. 每个宏至少 1 条**纯坐标策略**样例用于故障定位（感知失败时可复现）；
3. 涉及外部依赖（网络/登录态）的样例必须声明 `initialState` 并优先 Mock；
4. 每机型每宏的通过率**单独统计**，不得跨机型平均掩盖失败。

## 4. staged-enable 观察

### 4.1 状态流转（对齐 A8.1 `ASSET_STATUS_*`）

```
注册（第三方宏默认 STAGED=2，平台签名宏 ENABLED=0）
  → staged-enable 观察期（F1.2 回归数据收集）
  → 达标 → ENABLED
  → 未达标 / 连续失败 ≥3 → DISABLED（回灌 A8.1）
```

- 平台签名宏（系统内置）初始即 ENABLED，但**同样**进入观察期收集数据（可回退）；
- 观察期数据源：F1.2 `report.json`（回归期）+ A8.1 `reportExecution`（运行期）。

### 4.2 观察期门槛（staged → enabled）

| 指标 | 门槛 | 数据窗口 |
|---|---|---|
| 同机型黄金通过率 | ≥ 99% | 最近 14 天或 ≥ 30 次执行 |
| 连续失败 | 无 ≥3 次连续失败（1h 窗口） | 最近 14 天 |
| 失败率（样本 ≥5） | < 70% | 最近 14 天 |
| 版本漂移 | 无未确认漂移 | 与基线比对 |

> staged 状态下的宏**不进入生产解析链**（A8.1 `getToolDescriptors` 只返回 ENABLED），
> 但可被测试会话显式调用，以采集真实回归数据。

### 4.3 观察看板字段（供 D4.2/隐私仪表盘与 H 部门消费）

`{macroId, status, enableRatio（实际启用流量占比）, passRate, consecutiveFailures,
failureRate, driftStatus, stagedDays, lastRunAt}`

- `enableRatio`：staged-enable 的灰度放大节奏（可选：5% → 25% → 100%，对齐 A8.1 staged-enable 语义），
  放大的前提是当前档位通过率 ≥99%。

## 5. 通过率 ≥99% 验收配合

### 5.1 通过率口径（与 H 部门对齐，避免歧义）

- **分子**：同机型黄金样例中 `result=pass` 的用例数；
- **分母**：同机型黄金样例中**实际执行**的用例数（`fail`+`timeout`+`pass`）；
- **排除项**：`skip`（机型能力裁剪、offline）、`error`（重放基础设施不可用，单独报告）不计入分母；
- **统计窗口**：最近 14 天滚动；样本不足（<30 次执行）时以"无连续失败 + 无高失败率"替代判定，不直接判达标。

### 5.2 达标判定与验收联动

```
通过率 = pass / (pass + fail + timeout) ≥ 0.99
且 连续失败 < 3 且 无未确认版本漂移
→ 该机型该宏达标，可 staged → enabled，供 A5 验收
```

- 验收方：**H 部门实测为准**（WBS §9：H 是验收唯一出口，不得以"联调通过"替代）；
- F1.3 交付物：宏库 v1 + 每机型通过率台账（由 F1.2 `report.json` 聚合生成 `reports/ci/macro/` 下的台账），
  作为 A5 门禁（宏通过率 ≥99%）的证据输入。

### 5.3 不达标处置

| 情形 | 处置 |
|---|---|
| 通过率 <99% 但未触发停用 | 冻结 enable，标记"待修"，进入增量回归专项（§6.3） |
| 连续失败 ≥3 / 高失败率 | F1.2 自动停用回灌 A8.1，修复后重新 staged |
| 版本漂移 | `--update-baseline` 确认适配或停用 |
| 机型差异导致仅某机型失败 | 按 `deviceTags` 拆分：该机型降级该宏（或补坐标缩放），其余机型不受影响 |

## 6. 增量回归策略

### 6.1 全量 vs 增量

| 维度 | 全量回归（每日） | 增量回归（提交/每 4h） |
|---|---|---|
| 范围 | 全部 ENABLED+STAGED 宏 × 全部机型 | 受影响宏 × 受影响机型 |
| 触发 | `0 2 * * *` | 提交（`macros/**`）+ `0 */4 * * *` |
| 耗时预算 | 设备矩阵全量（可并行） | ≤ 15 分钟 |
| 用途 | 基线维护、A5 验收证据 | 快速反馈、门禁 |

### 6.2 影响面分析（增量范围判定）

增量回归只跑"受影响"的宏，判定规则（按优先级）：

1. **宏本体变更**：提交涉及 `macros/**` 或 `tests/macro/golden/**` → 跑该宏全部机型；
2. **机型档案变更**：提交涉及 `vendor/genton/config/calibration/profiles/<profile>.json`
   → 跑 `deviceTags` 含该档案的全部宏；
3. **依赖 App 变更**：`AssetUpdateInfo`（A8.1 onAssetChanged，changeType=updated）
   → 跑绑定该 App 版本范围的宏（版本漂移检测）；
4. **系统/框架变更**：提交涉及 `overlay/frameworks/base/services/.../genton/` 或 sepolicy
   → 触发全量回归（影响面不可枚举）；
5. **基线漂移确认**（F1.2 baseline 报告漂移）→ 跑漂移宏专项。

### 6.3 失败宏专项回归（回归失败后的收敛）

当某宏增量回归失败但未达停用阈值：

1. 单宏放大样本：同机型补 5–10 条变体样例（不同初始状态/参数）；
2. 三策略对拍：纯坐标 / 混合 / 纯感知分别重放，定位是坐标失效还是感知失效；
3. 结合 F4.2 校准回归样本（replay.hybrid.*）验证机型参数是否需要更新（如坐标缩放）；
4. 收敛后恢复 staged → 观察 → enable；无法收敛则停用并归档。

### 6.4 与 H4.1 真机矩阵的协作

- 执行器：H4.1 真机矩阵基线提供设备池与运行框架；F1.2 `replay` 作为宏回归执行器接入；
- 共享样例：F4.2 suite（校准基线）与 F1.3 golden（宏行为）并行执行、分别归档；
- 结果回写：H4.1 运行器将结果回写 `regression/*.suite.json` 的 `status`（draft → pending_device_run → verified），
  宏通过率台账由 F1.2 `report.json` 聚合。

## 7. 里程碑收口（A5）

| 交付物 | 验收证据 |
|---|---|
| 宏库 v1（per-机型黄金样例 ≥100 条级，宏数 40–60） | `tests/macro/golden/` 清单 + F4.1 档案引用 |
| per-机型通过率台账（≥99%） | `reports/ci/macro/` 聚合报告（F1.2 产出） |
| staged-enable 观察记录 | A8.1 资产状态 + 观察看板字段 |
| 增量回归策略落地 | CI 触发日志 + 影响面分析记录 |

**A5 门禁输入**：宏通过率 ≥99%（H 实测为准）+ 误预取 <2%（D9 KPI，H5.1 遥测）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 样本量不足导致通过率统计失真 | 明确最小样本（30 次执行）与替代判定（§5.1） |
| 机型差异导致跨机型平均掩盖失败 | per-机型单独统计（§3.4） |
| 外部依赖（网络/登录态）引入抖动 | `initialState` 声明 + Mock 优先（§3.4） |
| 全量回归耗时过长 | 增量回归 + 影响面分析（§6） |
| App 更新导致宏批量失效 | A8.1 版本绑定 + onAssetChanged 监听 + 版本漂移专项（§6.2.3） |
