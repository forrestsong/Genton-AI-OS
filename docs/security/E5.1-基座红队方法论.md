## 0. 结论摘要

本方法论定义基座红队（A1 门禁）的**四类攻击面**（令牌三查绕过、审计链篡改、确认链劫持、deny 默认绕过）的**测试用例集**（含具体攻击步骤/预期结果/判定），并配套 Python 冒烟脚本 `tools/redteam/base_redteam.py` 用于门禁前的自动化预检。

**红队判定规则**：
- **高风险（阻断 A1）**：攻击可导致「越权执行副作用」「篡改审计不可检出」「伪造确认通过」「绕过 deny 默认执行拒绝的动作」；
- **中风险**：信息泄露 / 越权读取但无副作用执行；
- **低风险**：健壮性问题（异常路径返回码不当等）。
- **门禁口径**：E5.1 红队**无高风险** → A1 通过（对齐 WBS 里程碑矩阵）。

**核心结论（预检基线）**：令牌三查（签名/scope/过期+撤销）必须全部 fail-secure；审计链哈希 + TEE 锚定防篡改；confirmId HMAC + 确认结果直回中介不经大脑；策略无匹配默认 DENY——**四条基线的攻击路径在本方法论中逐一列明验证方法**。

## 2. A1 令牌三查绕过（R1.11-R1.15）

### 2.1 用例 T1：签名伪造

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 攻击者（恶意 App/三方 Agent）自行构造 `CapabilityToken`，篡改 `agentId`/`capability`/`expiresAt`；② 伪造 `issuerSignature`（用自己生成的密钥签名，或留空/截断）；③ 调用域服务 `validateToken` 或直接提交动作请求 |
| 预期结果 | 签名校验失败 → 拒绝（fail-secure，不降级到 UID 校验） |
| 判定 | 通过 = 任何伪造签名令牌被拒且**不产生副作用**；失败 = 存在「签名失败降级到其他校验」或「不验签直接放行」 |
| 冒烟 | `base_redteam.py --case token-forge`（构造篡改签名令牌断言拒绝） |

### 2.2 用例 T2：scope 跨意图盗用

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 正常获取某 intent 的令牌（scopeIntentId=it-A）；② 将该令牌用于**另一意图 it-B** 的动作请求（改变 `sourceIntentId`）；③ 或把「查短信」令牌用于「发短信」动作（capability 不匹配） |
| 预期结果 | `validateToken` 校验 `scopeIntentId == 动作.sourceIntentId` 且 capability 匹配，不匹配 → 拒绝 |
| 判定 | 通过 = 跨意图/跨能力令牌被拒；失败 = 令牌可跨 scope 复用 |
| 冒烟 | `base_redteam.py --case token-scope` |

### 2.3 用例 T3：过期令牌重放

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 抓取合法令牌；② 修改系统时间/等待 TTL 到期（R1.12 ≤5min）；③ 重放令牌发起动作 |
| 预期结果 | 过期立即失效，**无宽限期**（fail-secure） |
| 判定 | 通过 = 过期令牌被拒；失败 = 存在宽限期或时钟回拨可利用 |
| 冒烟 | `base_redteam.py --case token-expired` |

### 2.4 用例 T4：撤销绕过（R1.15 ≤100ms）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 获取合法令牌；② 调用 `revokeTokens(agentId, intentId)` 撤销；③ 立即（<100ms）重放令牌动作；④ 或利用「离线验签缓存」（D10 §3.2）在撤销广播到达前重放 |
| 预期结果 | 在线撤销状态实时生效（≤100ms）；撤销后重放被拒 |
| 判定 | 通过 = 撤销后重放被拒（含缓存窗口 TTL 内）；失败 = 撤销后令牌仍可用 |
| 冒烟 | `base_redteam.py --case token-revoke` |

### 2.5 用例 T5：撤销列表查询失败 fail-secure

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 注入撤销列表服务异常（进程 kill/存储损坏/IPC 超时）；② 用合法令牌发起动作 |
| 预期结果 | 撤销检查失败 → 拒绝（fail-secure，R2.2 令牌红线） |
| 判定 | 通过 = 异常时拒绝；失败 = 异常时放行 |
| 冒烟 | `base_redteam.py --case token-failsecure` |

## 3. A2 审计链篡改（R8.1-R8.5）

### 3.1 用例 A1：链中删事件

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 记录事件 seq=1..N；② 删除中间事件 seq=k（从持久化文件/数据库删除）；③ 调用 `verifyChain(1,N)` |
| 预期结果 | 删除 → 前向指针 `prevHash` 断裂 → `ChainStatus.brokenAtSeq=k` |
| 判定 | 通过 = verifyChain 检出断裂；失败 = 删除后链仍完整 |
| 冒烟 | `base_redteam.py --case audit-delete` |

### 3.2 用例 A2：改事件内容（篡改 summary）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 记录事件；② 修改 `summary`/`category`/`agentId` 字段；③ verifyChain |
| 预期结果 | 字段变更 → 该事件 hash 不匹配 → brokenAtSeq |
| 判定 | 通过 = 检出；失败 = 内容可改而不检出 |
| 冒烟 | `base_redteam.py --case audit-tamper` |

### 3.3 用例 A3：重放/回滚攻击

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 用旧快照覆盖审计存储（回滚到最后锚点之前的某状态）；② verifyChain 与 TEE 锚点比对 |
| 预期结果 | TEE 锚点序号/哈希不匹配 → 检出「锚点之后事件缺失」（防回滚需锚点序号单调递增） |
| 判定 | 通过 = 回滚被锚点检出；失败 = 锚点不覆盖（回滚不可检出） |
| 冒烟 | `base_redteam.py --case audit-rollback`（模拟锚点序号回退） |

### 3.4 用例 A4：越权写审计（非系统服务伪造事件）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 非特权进程调用 `record()` 写入伪造 `CAT_ACTION_EXECUTE` 事件；② 或伪造 `agentId` 嫁祸 |
| 预期结果 | `record()` 仅系统服务/特权大脑可调（R8.1），非特权被拒 `STATUS_DENIED`；`agentId` 由服务校验（签名调用方身份） |
| 判定 | 通过 = 越权写被拒；失败 = 可伪造写入 |
| 冒烟 | `base_redteam.py --case audit-unauth-write` |

## 4. A3 确认链劫持（R5.1-R5.10）

### 4.1 用例 C1：伪造 confirmId

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① Agent 自行构造 `confirmId`（猜测 HMAC 或复用旧值）；② 调用 `reportUserDecision(confirmId, USER_ALLOW)` |
| 预期结果 | confirmId 由策略引擎 HMAC 签发（D10 §3.1），伪造被拒；复用已消费 confirmId 被拒（防重放） |
| 判定 | 通过 = 伪造/重放被拒；失败 = 可伪造通过 |
| 冒烟 | `base_redteam.py --case confirm-forge` |

### 4.2 用例 C2：确认超时抢占（R5.7）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 发起需确认动作；② 用户未操作，超时后攻击者提交 USER_ALLOW（抢占过期会话） |
| 预期结果 | 确认超时 → 状态 EXPIRED → 任何迟到的 reportUserDecision 被拒、动作不执行 |
| 判定 | 通过 = 超时后提交被拒且不执行；失败 = 超时后仍可确认执行 |
| 冒烟 | `base_redteam.py --case confirm-expired` |

### 4.3 用例 C3：确认面板非独占 / 结果经大脑回灌

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 构造自绘 Dialog（Agent 自我确认）替代 SystemUI 面板；② 或让确认结果「先经大脑再回执行中介」（R5.5 禁止） |
| 预期结果 | 确认面板只能 SystemUI 展示（R5.1）；`ConfirmationUiRequest` 来源验证；确认结果直回执行中介（不经大脑） |
| 判定 | 通过 = 非 SystemUI 确认被拒 + 回灌路径不含大脑；失败 = 存在大脑回灌/自绘确认 |
| 冒烟 | `base_redteam.py --case confirm-host`（静态校验确认宿主归属） |

### 4.4 用例 C4：免确认绕过（R5.9/R5.10）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① Agent 尝试修改免确认开关（R5.9 系统级设置，Agent 不可改）；② 或把 high 风险动作降级为 low 以绕过强制确认（R5.10） |
| 预期结果 | 免确认开关系统级只读（Agent 改被拒）；high 风险即使免确认开启仍强制确认 |
| 判定 | 通过 = 两项都被拒；失败 = 可改开关 / 可降级绕过 |
| 冒烟 | `base_redteam.py --case confirm-riskdowngrade` |

## 5. A4 deny 默认绕过（R2.1-R2.10）

### 5.1 用例 D1：无匹配规则请求

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 提交未注册能力/未匹配规则的意图（`unknown.capability`）；② 观察策略引擎返回 |
| 预期结果 | 无匹配 → 授权轴 `DEC_DENY`；路由轴 `P0_NATIVE`/`RING_NATIVE`（可见，不静默）；未知能力 `STATUS_UNKNOWN_CAP` 视为 deny |
| 判定 | 通过 = 默认 DENY/native；失败 = 默认 ALLOW/UNKNOWN |
| 冒烟 | `base_redteam.py --case deny-nomatch` |

### 5.2 用例 D2：基线覆盖（R2.4）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 配置 user 规则尝试覆盖 baseline-deny-protect（如把闹钟 P0 改为可静默、把紧急号码改为可拦）；② 冲突矩阵/编译校验 |
| 预期结果 | baseline 优先不可被 user/learn 覆盖；编译期冲突矩阵拒绝（D17 C6） |
| 判定 | 通过 = baseline 不可覆盖 + 冲突被拒；失败 = user 规则可覆盖 baseline |
| 冒烟 | `base_redteam.py --case deny-baseline` |

### 5.3 用例 D3：策略编译失败 fail-stop（R2.5）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 注入损坏的 DSL 策略包（语法错误/冲突）；② reloadPolicySet；③ 观察系统行为 |
| 预期结果 | 编译失败 → 拒绝启动 / 回滚上一版 + 停发新令牌（fail-stop，R2.5/R13.2） |
| 判定 | 通过 = fail-stop + 回滚 + 停令牌；失败 = 坏策略被接受或系统带病启动 |
| 冒烟 | `base_redteam.py --case deny-failstop` |

### 5.4 用例 D4：通知路由静默吞（R2.2）

| 项 | 内容 |
|---|---|
| 攻击步骤 | ① 无匹配路由规则的通知（应 P0 原生可见）；② 或 user 规则尝试把 P0/闹钟折叠 |
| 预期结果 | 无匹配 → P0_NATIVE 原生可见；P0 钉选不可折叠（baseline-deny-protect） |
| 判定 | 通过 = 可见（不静默吞）；失败 = 通知被静默折叠 |
| 冒烟 | `base_redteam.py --case deny-notification` |

## 6. 配套冒烟脚本 `tools/redteam/base_redteam.py`

### 6.1 用途

A1 门禁前的**自动化预检**：对上述用例做可脚本化部分的冒烟验证（令牌/审计/确认/deny 的逻辑级模拟 + 静态红线扫描），输出 PASS/FAIL 与退出码（0=无高风险，1=发现高风险）。

### 6.2 用法

```bash
python tools/redteam/base_redteam.py --all            # 全量冒烟
python tools/redteam/base_redteam.py --case token-forge   # 单用例
python tools/redteam/base_redteam.py --list           # 列出用例
```

### 6.3 限制与人工补充

- 冒烟脚本覆盖**逻辑级与静态红线**验证（含 TEE 不可导出、confirmId HMAC、审计哈希链的静态/模拟校验）；
- **真机动态验证**（真实 TEE、真实 InputDispatcher 注入、真实进程隔离）由 H3.1 e2e + 红队人工执行本方法论 §2-5 的完整用例，**冒烟脚本不替代真机红队**。

## 8. 遗留项

1. **真机动态红队执行排期**：A1 门禁前由安全合规部 + H 部组织（对齐里程碑矩阵）。
2. **误报/漏报度量**：令牌离线验签缓存窗口（D10 §3.2）的实际撤销时延需实测登记。
3. **多 Agent 并发确认竞态**：confirmId 并发消费的边界（D10 开放问题 3）纳入真机红队。
